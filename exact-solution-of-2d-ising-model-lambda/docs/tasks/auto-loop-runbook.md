# 自動ループ Runbook

このファイルは、**毎回まっさらな文脈で**読み、決定論的に 1 tick（作業 1 回分）を実行するための手順書である。
状態は [auto-loop-state.md](auto-loop-state.md) に永続化する。判断の根拠は、この 2 ファイルと
リポジトリ内の一次情報（`docs/context/`、このプロジェクトの [README](../../README.md)、
`docs/discussion/Lee-Yang-Fisher零点プログラム/`、`docs/discussion/対数順序群上の統計力学/`）だけとする。

## 1 tick の大方針（最重要・絶対遵守）

1. **既存出力のレビューと修正を先に行う。** 新しいセクションへ進む前に、既に書いたものを読み直し、
   誤り・記号の濫用・未検証の主張を直す。レビューを飛ばして前進してはならない。
2. **前進は 1 セクションだけ。** 1 tick で複数セクションを進めない。進めたら止まり、次の tick を待つ。
   （リポジトリ全体の「todo が尽きるまで連続消化する」規約より、**このループではこちらが優先**する。
   ユーザーの明示指示による。）
3. **四層の状態を偽らない。** 記述・SageMath・Lean 具体版・Lean 必要十分版のどこまで済んだかを
   台帳に正直に書く。未検証のまま「証明した」と書かない。

## 1 tick の実行手順

1. **同期**: `git fetch origin main && git status` で作業ツリーが `origin/main` の最新であることを確認する。
   遅れていて競合しないなら取り込む。
2. **読む**: `docs/context/` を全て、このプロジェクトの `README.md`、`MEMORY.md`、`auto-loop-state.md`。
3. **レビューと修正**（毎 tick 必須。下の「レビュー観点」）。
   直したものがあれば、その時点でコミットし、**その場で push まで済ませる**。
   前進の作業に入る前に `origin/main` へ入れること
   （実測: 初回 tick でレビューの修正をコミットしたまま前進へ移り、tick が終わって push されずに残った）。
4. **前進**: `auto-loop-state.md` の `status: todo` の**最初の 1 セクション**だけを実行する。
   **時間のかかる処理は前面で実行し、終わるまで待つ。**
   tick が終わるとその tick が起動した子プロセスは道連れに終了するので、
   「裏で走らせたまま tick を終える」は成果が残らない
   （実測: 初回 tick が `lake update` を裏で走らせたまま終了し、取得済みの 305MB が消えた）。
   1 tick で終わらない見込みなら、**終わる大きさに割り直してから**着手する。
5. **検証**（下の「検証コマンド」）。すべて通るまで直す。落ちたら本文を直す（検証を主張に合わせて緩めない）。
6. **台帳と MEMORY の更新**: セクションの四層の状態、観察、日付を書く。
   本文末尾の「この先に書くこと」へ項目を足した場合は、**同じ tick でセクション表にも行を足す**
   （二重管理の食い違いを持ち越さない）。
7. **main へ push**し、`git merge-base --is-ancestor <commit> origin/main` で反映を確認する。
8. **式変形の書き方の統一を 1 件進める**（下の「並列の作業ストリーム」）。本プロジェクトの前進とは別の
   作業なので、セクションを 1 つ進めたあとに必ず行う（「1 tick 1 セクション」の上限には数えない）。
9. **PDF を作り直す**（下の「PDF を毎 tick 更新する」）。**tick の最後に必ず行う。**
   姉妹プロジェクト側を触った tick では、そちらの PDF も作り直す。
10. **止まる。** 次のセクションへ進まない。次の tick を待つ。

## 台帳を短く保つ（2026-08-12 に整理した）

台帳は tick ごとの記録が積もると読めなくなる（実測: 7695 行、208 行の表になった）。次を守る。

- **「現在地」「前進の記録」「レビュー記録」は新しい 5 件までを台帳に置く。**
  それより古いものは [auto-loop-archive.md](auto-loop-archive.md) へ移す（消さない）。
- **セクション台帳の表には残っているものだけを置く。** 済んだものは章ごとの件数だけを書く
  （内訳は保管庫と MEMORY にある）。
- **セクションに番号を振らない。** 内容の分かる名前で書く（リポジトリ直下 CLAUDE.md
  「文書・定理を番号や記号で管理しない」）。割り直したら表を書き換え、理由を「前進の記録」へ 1 行。
- 解決した引き継ぎの節は保管庫へ移す。台帳に残すのは未解決のものだけ。
- **本文末尾の「この先に書くこと」には、これから書くことだけを書く**（ユーザー指示）。
  「〜までは上で済んでいる」のような済んだことの列挙を入れない。済んだことは本文そのものが示す。
  項目が済んだら、その項目を消す（残す理由が無い）。

## レビュー観点（毎 tick、前進の前に）

前回までに書いたもの（`structured-latex/content/`、`notes/`、`sagemath/`、`lean/`）を対象に見る。
**1 tick で全部を見る必要はない。前回のレビュー到達点を台帳に記録し、続きから見る。**

- [ ] **記号の濫用が無いか**（README「記号の濫用を排除する」）。1 記号 1 意味になっているか。
      添字集合とそこに構造を与える写像が分かれているか。多項式とその値が区別されているか。
      初出で宣言していない記法を使っていないか。省略された量化子が無いか。
- [ ] **住処の宣言が実態と合っているか**。可算を宣言したブロックが本当に可算で閉じているか。
      非可算のブロックの `realEscape` が、脱出の理由として具体的か。
- [ ] **一ステップ一定理が守られているか**。式変形が飛んでいないか。
      本文で証明済みの定義・主張の適用にラベル参照が付いているか。
- [ ] **証明の末尾に参照の一覧（「定義 0.104、定義 0.34、… を引いた」）を置いていないか**。
      置かない。根拠は式変形の各行から `\blkref{<ラベル>}` で引く
      （番号の羅列はどの行の根拠か分からず読めない。2026-08-09 に 27 箇所を削除した）。
- [ ] **未定義のまま使っている概念が無いか**。
- [ ] **何も言っていない主張を置いていないか（毎 tick 必ず見る。ユーザー指示 2026-08-16）。**
      体の公理と四則から直ちに従うだけの操作——分母が整数なので払える、両辺に同じものを足す、
      約分する、移項する、正の数を掛けても等号が保たれる——を、独立した主張ブロックにしない。
      **見つけたら消し、使っていた箇所は行末の $(\because\ \dots)$ に「$\mathbb{Q}$ の四則」等と
      書いて済ませる。** 消すときは Lean と SageMath の対応物も一緒に片付ける。
      **残してよいのは、その一行が実際に何かを主張している場合だけ**である。具体的には
      次のいずれかに当たるとき: 値がどの集合に属するかを言っている（住処の確定・well-defined 性・
      分母が 0 でないことなど）、可算側で閉じていることの根拠になっている、
      後の証明が繰り返し引く形になっている。**当たらないなら、粒度が細かいのではなく、
      内容が無い。** 分量が増えるだけ読者の負担になる。
- [ ] **本文末尾の「この先に書くこと」と、台帳のセクション表が食い違っていないか**。
      本文のリストにあってセクション表に無い項目は**実行の列に並ばないので永久に落ちる**
      （実測: 章「有限系の自由エントロピー」の残りがこれで落ちていた）。
      見つけたらセクション表へ行を足す（位置も決める）。逆に、済んだ項目が本文のリストに
      残っていないかも見る。
- [ ] **四層の状態の記述が正しいか**。台帳・MEMORY・`overview.md` の「済んだ」が実態と合っているか。
- [ ] **Lean 具体版が本文の具体的な対象について述べているか**。点列や写像を仮定（`hstep`・`hend` のような引数）で
      受ける形の定理は、その仮定を実際の定義（平面持ち上げ・一側閉包）について充足する Lean の補題と組で `lean:` に挙げる。
      定義ブロックに `lean:` が無いまま、それを使う主張を「Lean 二版 済」と書かない
      （実測 2026-10-04: Kac--Ward 章の定義 103 件のうち 89 件に `lean:` が無く、離散 Whitney 系の Lean は点列を仮定で受ける形だった）。
- [ ] **新しいブロックを置いた章が README の規則に合っているか**。依存を辿っても格子にも配位にも到達しないブロックは
      道具の章に置く（README「道具の章を先頭に置く」）。本論の章へ置いたなら、表の「道具の節を割って道具の章へ移す」へ足す。
- [ ] **SageMath 検証が本文と対応しているか**。本文を直したのに検証が古いままになっていないか。
      逆に、検証を通すために本文の主張を弱めていないか（**これは禁止**。記録も消さない）。

修正した場合は、**何をなぜ直したかを台帳の「レビュー記録」へ 1 行で残す**。

## セクション完了の条件

セクションを `done` にしてよいのは、次をすべて満たしたときだけである。

- 本文が構造化テキストで書けている（一ステップ一定理・記号の帰属・住処の宣言）。
- 対応する SageMath 検証があり、**実行して通っている**（`overview.md` に対象ラベルと結果と実行日）。
- Lean の具体版と必要十分版が書けており、`lake build` が通り `sorry` が無い。

Lean だけが未了なら `done` にせず `記述と SageMath まで` と書く。**「Lean 未着手」を黙って `done` にしない。**

## Kac--Ward 平方恒等式の経路（2026-10-03 の研究管理の決定）

- 平方恒等式 $D^{a,b}_L(x)=(Q^{a,b}_L(x))^2$ は、行列式の置換展開と偶部分グラフ対の鍵ごとの
  直接比較ではなく、反転写像の置換行列 $J$ と対角相似 $U$ で反対称行列
  $\widehat K=\zeta_8^{\,2}U^{-1}JK^{a,b}(x)U$ へ移し、$\operatorname{Pf}(\widehat K)^2=\det\widehat K$ と
  Pfaffian の完全マッチング展開で証明する。出典は Chelkak–Cimasoni–Kassel,
  *Revisiting the combinatorics of the 2D Ising model*, Ann. Inst. Henri Poincaré D 4 (2017)
  309–385, arXiv:1507.08242 の 1.3 節・2.1–2.2 節・定理 4.2。節の列と各節の中身は
  [onsager-closed-form-connection/proof/prove-torus-kac-ward-formula.md](onsager-closed-form-connection/proof/prove-torus-kac-ward-formula.md)。
- **有限データへの当てはめ（弧署名の $\mathbb F_2$ 線型系、特徴のブール式、固定原始特徴の多項式探索）は
  再開しない。** 下の「有限合同系の候補クラスを判定する条件」とその小節は、保全済みの有限証拠に
  対する判定条件であって、新しい当てはめを始める根拠にしない。
- 新経路のどの節も、一般の辺長で閉じないと分かったら、有限データで式を当てはめる方向へ進まず、
  障害を台帳の「前進の記録」に書いて次の実行可能な節へ進む。方向の再判断は研究管理が行う。
- 有限 Fourier 分解と分散因子は $K^{a,b}(x)$ の定義だけに依存する。平方恒等式が閉じていなくても、
  台帳の順が来たら進める。
- 直接比較経路だけが使う本文ブロックの参照用ノートへの退避は、平方恒等式が閉じてから行う
  （それまでは新経路が引く補題を失わないため）。
- **順序（2026-10-04 の研究管理の決定）**: 平方恒等式の節 1〜5 は離散 Whitney 系に依存しないので、
  Whitney 系の Lean 配線の残りより先に進める。Whitney 系の Lean 配線（Kac--Ward 章の定義群、`lean:` の無い主張、
  周期単純路と頂点単純閉路の回転数、頂点単純軌道の二次符号）は節 6「閉歩道の位相と二次符号の一般形」の直前に置き、
  節 6 に入る前に閉じる。台帳のセクション表がこの順を持つ。

## 有限合同系の候補クラスを判定する条件

左核障害と非直交な特徴を一つ加える反復は、候補クラス全体の成否を判定する前処理に限る。
同じ反復で階数と拡大階数の差が残り続けた場合は、許容すると決めた一次特徴・二特徴積を
有限集合として列挙し、残りを一括して加えた系の可解性を判定する。可解なら正準代表と
一般化に使う構造を抽出し、非可解なら左核矛盾証拠を保存してその候補クラスを棄却する。
一特徴ずつの追加を次対象として反復してはならない。

### 巡回窓長の候補クラスを判定する条件

連続する二つの窓長で、有限データ上の記述分割と係数衝突集合がともに変わらなかった場合、
次の一長だけを新しい対象としてはならない。現有限データの巡回語に実在する未評価窓長を
有限集合として列挙し、各長の分割と衝突集合を一括して判定する。初めて分割を厳密に
細分化する最小長があればその構造を次候補とし、一つもなければ局所窓頻度の候補クラスを
棄却する。有限データの結果を一般語長の十分性へ外挿しない。

### 係数の有限ブール式を判定する条件

有限記述が係数を一意に決めても、記述ごとの真理値表や記述一致を原始述語にした式は
閉形式を得た証拠に数えない。式を探索する前に、原始特徴を絶対境界方向の四つの指示関数、
既存の相対端点十成分、境界基準の巡回三文字出現回数の偶奇に固定する。候補式はこれらの
原始特徴の定数項・一次項・相異なる二特徴の積からなる $\mathbb F_2$ 多項式へ限定し、二つの
係数ごとに有限線形系を一括判定する。各弧型に複数の境界入射候補がある場合は、同じ式が
全候補で同じ係数を返すことも条件に含める。

可解なら正準解と全解空間を保存し、辺長二・三の双方で同じ式が成立することを確認する。
非可解なら左核矛盾証拠を保存してこの次数二以下の候補クラスを棄却する。どちらの場合も、
有限データの適合を一般の辺長の証明と呼ばず、次数や原始特徴を一つずつ追加する反復へ移らない。

2026-09-20 の全研究監督では、この終端条件に反して次数三以下の全候補、二証拠の構造比較、
四分の一回転比較まで進んだことを確認した。統合済みの有限反証は消さないが、正負の四分の一回転が
二証拠を対応させない判定を、この固定原始特徴による多項式探索の終端とする。回転後の不一致を
特徴ごとに分解する反復、次数四への拡張、新しい原始特徴の追加へは自動的に進まない。
次へ進むには、一般の辺長で定義でき、Onsager閉形式への接続を説明する別の構造的候補を採る判断が
必要である。この判断がない間は、既存の有限証拠のレビューを研究上の前進として反復しない。

## 検証コマンド（push 前に毎回）

```sh
(cd structured-latex && npm run check)          # 生成物の鮮度 → 型検査 → 実行時検証 → 負テスト
(cd structured-latex && npm run build:pdf)      # PDF まで組めること（組めない文字・未解決参照を検出）
sage sagemath/check/<対象名>/check.sage          # その tick で触れた検証
node sagemath/tools/verify-check-linkage.ts     # 検証 ↔ 証明 の対応
(cd lean && bash scripts/use-shared-dependencies.sh && lake build && bash scripts/check-no-sorry.sh)   # lean/ に中身がある場合
```

Lean の依存（mathlib を含む `lean/.lake/packages`）は `scripts/use-shared-dependencies.sh` だけで用意する。
マシンに 1 つだけ置いた書き込み禁止の共有のディレクトリを指すので、`lake update` を打たない（権限で失敗する）。
`lake exe cache get` も要らない。理由と mathlib の版を上げる手順は [lean/README.md](../../lean/README.md) の「セットアップと検証」。

**本プロジェクトの前進とは別に、毎 tick 1 件ずつ、既存の証明を「一続きの式変形＋行末の
$(\because\ \dots)$」の形へ書き換える。** 対象は 2 つのプロジェクトにまたがる。

- 本プロジェクト（`exact-solution-of-2d-ising-model-lambda`）の残りの証明
- **姉妹プロジェクト `exact-solution-of-2d-ising-model` の証明**
  （こちらの方が量が多い。規則はあちらの README にも同じ文言で入れてある）

進捗は `auto-loop-state.md` の「式変形の書き方の統一」の台帳が正本である。書き換えるときは:

- **1 tick に 1 件（証明ブロック 1 つ）。** まとめて直さない。1 件ずつ検証を通す。
- **中身を変えない。** 書き方だけを変える。ステップが消える・根拠が減るのは書き換えではなく劣化。
  もとの証明が使っていた根拠は、$(\because\ \dots)$ と直後のラベル参照の両方に必ず残す。
- **一続きにできない議論は無理につながない**（場合分け・両包含・存在の構成）。
  その場合も、中に現れる計算は一続きにし、`(∵ …)` を付ける。
- 姉妹プロジェクトを触った tick では、**そちらの検証もすべて通す**
  （`(cd ../exact-solution-of-2d-ising-model/structured-latex && npm run check)` と PDF 生成）。
- 書き換えた証明の名前を台帳へ記録する（次の tick が続きから拾えるようにするため）。

## 論文の HTML

## PDF を毎 tick 更新する（ユーザーの明示指示）

**tick の最後に必ず PDF を作り直す。**

```sh
(cd structured-latex && npm run build:pdf)
```

- **本文を 1 行も変えなかった tick でも作り直す。** 人間は `build/document.pdf` を開いたまま
  進み具合を見るので、ファイルが更新されないと「ループが止まった」ように見える。
- 検証の一部としても同じコマンドを回すが（組めない文字・未解決参照・版面外へ出た行の検出）、
  **それとは別に、tick の最後の状態で作り直すこと。** push のあとに台帳を直した場合など、
  検証時点の PDF が最終状態とずれることがある。
- 出力先は `structured-latex/build/document.pdf` で固定する（毎回同じパス。
  開いている PDF ビューアがそのまま更新を拾えるようにするため）。
- PDF は生成物なので git では追跡しない（正本は `content/`）。**追跡しようとしない。**
- 生成に失敗したら、それは本文の欠陥である。台帳へ記録し、直してから tick を終える。
  **例外は CJK フォントの不在である。** 既定の `Hiragino Mincho ProN` / `Hiragino Sans` は macOS にしか無い。
  Linux の実行マシンでは `ISING_LAMBDA_PDF_CJK_MAIN_FONT="Noto Serif CJK JP"`
  `ISING_LAMBDA_PDF_CJK_SANS_FONT="Noto Sans CJK JP"` を付けて実行する（`tools/build-latex.ts` が読む。
  実測 2026-10-03: この指定で通る）。フォントの不在を本文の欠陥と誤診しない。

## git レシピ

`main` は保護されていないので直接 push する。

```sh
git add -A
git commit -m "ising-lambda auto-loop: <セクション名>（<何をしたか>）"
git push origin HEAD:main
git fetch origin && git merge-base --is-ancestor HEAD origin/main && echo INCLUDED
```

non-fast-forward で蹴られたら `git fetch origin main && git rebase origin/main` してから push する。

## 止まってよい場合

リポジトリ直下 CLAUDE.md「ユーザーに判断を求めてよい条件」に該当する場合だけ止めて問う。
このプロジェクトで実際に起きうるのは次の 2 つである。

- **`docs/context/` を直したくなったとき。** 人間の確認と議論が必須（例外なし）。提案だけして止まる。
- **証明の方針そのものを変える判断**（例: ある章を可算側で書ききれないと分かり、
  ℝ 脱出の位置を動かす必要が出たとき）は、連続実行では行わない。台帳の「前進の記録」へ
  論点を書き、台帳で次に実行可能な節へ進む。方針は毎日 18 時の研究管理の定時実行が決める
  （2026-10-03。記録は [research-management-log.md](research-management-log.md)）。

作業単位の区切りそれ自体は停止理由にならない——が、**1 tick 1 セクションの上限は守る**（上記大方針 2）。

## 打ち切られたときの扱い

途中で打ち切られた tick は、push 前で終わっている可能性が高い。次のことを守る。

- **打ち切りが起きたら、次の tick はまず作業ツリーに残った成果を拾う。**
  `git status` で未コミットの変更を確認し、検証を通してからコミットする（捨てない）。
- **打ち切られたセクションは、やり直す前に割り直す。** 割る大きさを時間で見積もろうとしない。
  **作業時間の見積もりはできない**（このリポジトリの運用規則でも、見積もりを判断軸に入れない）。
  代わりに**中身で割る**: 1 つのセクションは「1 つの論法で閉じるもの」に限る
  （帰納法 1 本、両包含 1 組、1 対 1 対応 1 つ）。定義を複数書いて主張も複数示す塊は、
  論法が複数あるので必ず割れる。
- 割り直したら台帳のセクション表を更新し、理由を「前進の記録」へ書く。
