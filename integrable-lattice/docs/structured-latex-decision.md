# 構造化テキスト基盤: 共有ライブラリにせず複製した理由と、腐らせない仕組み

`integrable-lattice/structured-latex/` は
`exact-solution-of-2d-ising-model/structured-latex/` の実装を **複製**したものである。
共有ライブラリとして切り出していない。その判断の根拠と、複製の弱点への対処を記録する。

## 1. 実測: どこが同じで、どこが違うか

複製した時点で、両者のファイルを機械的に突き合わせた結果（`diff` の差分行数）。

| ファイル | 差分行 / 総行 | 性質 |
|---|---|---|
| `tools/content-modules.ts` | **0** / 74 | ドメインを知らない土台（ファイル読み込み） |
| `tools/generate-index.ts` | **0** / 218 | 同（生成物の作成） |
| `tools/latex-escape.ts` | **0** / 27 | 同（地の文のエスケープ） |
| `tools/verify-no-notes-in-output.ts` | **0** / 107 | 同（ノート非混入の検査） |
| `tools/validate-content.ts` | 119 / 260 | 住処と数式の食い違い・検証ディレクトリ実在の検査を追加 |

## 2. なぜ共有ライブラリにしなかったか

### (a) 共有できるのは土台だけで、要になる部分は共有できない

型検査の効き目を生んでいるのは、`content/` から生成する `labels.generated.ts` と
`document.generated.ts` である。これらは**各プロジェクトの content に強く結びついた生成物**で、
共有のしようがない。スキーマも、本プロジェクトは可算／非可算の分別（`habitat`）と
ℝ 脱出（`realEscape`）を**必須フィールドとして型で強制**しており、Ising 側とは別の型である。

### (b) 共有は、片方の都合でもう片方を落とす

Ising 側は複数セッションが並行で証明を書いている。共有ライブラリにすると、本プロジェクトの
都合でスキーマやツールへ手を入れた瞬間に、**あちらの検証・PDF 生成が落ちうる**。
この基盤の価値は「壊れたらすぐ落ちること」なので、落ちる理由が他プロジェクトの事情である状態は
価値を損なう。

### (c) 依存の向きを一方通行にできる

複製なら、Ising 側は本プロジェクトの存在を知らないままでよい（実際、Ising 側の
`npm run check` は本プロジェクトを一切参照しない）。

## 3. 複製の弱点と、その対処

複製の弱点は **片方だけ直してもう片方が腐る**ことである。これを機械で見る。

`tools/verify-shared-tools-in-sync.ts`（`npm run check` に組み込み済み）が次を検査する。

1. 上表で「差分 0」であるべき土台 4 ファイルが、複製元と**バイト一致**していること。
   → 片方で直した不具合が、もう片方へ運ばれていない状態を検出する。
2. 意図的に違えている 6 ファイルが、**complete に一致していない**こと。
   → 複製元の内容で上書きして、プロジェクト固有の検査を失う事故を検出する。
3. 複製元が見つからない場合は、検査を飛ばさず**エラーにする**
   （黙って飛ばすと、検査があるように見えて何も見ていない状態になる）。

**この検査は本プロジェクト側だけで走らせる。** Ising 側の `check` からは呼ばない
（あちらを本プロジェクトの都合で落とさないため）。

## 4. 将来、共有へ切り替えるとしたら

土台 4 ファイル（426 行）だけを小さなパッケージへ切り出す形なら成立する。判断材料は
「土台が 3 つ目のプロジェクトでも同一のまま使えるか」であり、2 プロジェクトの現時点では
複製の方が安全であると判断した。切り替えるときは、上記の同期検査をパッケージ参照へ置き換える。
