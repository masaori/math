# 被覆の数値の照合が実際に効いていることを毎回示す（cycle 29 step 6）

対象は検査側 1 ファイルだけである（`structured-latex/tools/verify-formalization-coverage.ts`）。
台帳（`formalization-coverage.ts`）・本文・Lean は本 step の担当外なので恒久的には触っていない
（本文は検出の実証のために一時的に書き換え、元へ戻して diff が空であることを確認した）。

## 何が問題だったか（一次情報）

cycle 28 step 6 は「本文が書いている被覆の数値」と「台帳の実測値」の一致を検査にしたが、
同じ step が自分の限界としてこう書き残していた——照合しているのは地の文の文字列なので、
本文が数を数式ノードで書くようになれば空振りする。いまは 0 件だが空振りしても静かなままである。

着手時の実測で、実装がその形であることを確認した。地の文だけを連結し（数式ノードは連結の前に落とす）、
`String.includes` で部分文字列を見て、一致しなければ違反にする。出力は
「本文が書いている被覆の数値: 2 箇所 / 4 文を台帳の実測値と突き合わせた」だけで、
**その 2 箇所・4 文が本当に何かを固定しているかは何も言っていなかった。**

読み直して分かったのは、空振りの道が 3 つあることである。

1. 照合する箇所そのものが無い。台帳の登録が空になっても、あるロケールが落ちても、
   件数が 0 になるだけで違反にならない（`0 箇所 / 0 文` と印字して緑になる）。
2. 照合する文字列が台帳の数に依っていない。数を含まない地の文の断片だけを照合していても、
   件数は増えるし一致もする。**この道が一番危ない**——数式ノードへ数が移ったときに
   照合が一致しなくなるので、直す人が「数を含まない断片」へ書き換えれば静かに通ってしまう。
3. 本文が数を数式ノードで書く。地の文の側からは数が消えるので、上の 2 の書き換えを誘発する。

## 採った設計とその理由

**地の文だけを照合する実装は変えず、空振りする 3 つの道をそれぞれ違反にした。**
理由は、照合が固定すべきものが「読者が読む文（＝ PDF に出る地の文）に台帳の数が書かれていること」
だからである。数式ノードの TeX を照合対象へ混ぜると、`$24$` のような書き方が通ってしまい、
何を固定しているのかが曖昧になる。数式に数が現れることは（照合できない形になったという意味で）
異常として扱うほうが、判断が一箇所に集まる。

- **期待件数を下回ったら赤くする。** ロケールごとに 1 箇所以上、各箇所 1 文以上を要求する。
  根拠は本文の側にある——形式検証の到達点の段は日英とも被覆を数で述べている。
  期待の根拠と実績（箇所数・文数）を毎回印字する。
- **台帳の数を 1 ずつ動かして、照合が動くことを確かめる。** 4 つの数（全数・完了・部分的・未着手）
  それぞれについて、その数を 1 増やした文字列を組み立て、
  **本文に在った文が本文から外れること**を確かめる。外れなければ、その数は照合で固定されていない。
  これは検査そのものを毎回自分で試す形なので、上の道 2 を塞ぐ。
  判定は「増やす前の文が本文に在り、増やした後の文が本文に無い」の両方を要求する
  （片方だけでは、照合が成り立っていない状態を固定と誤認する）。
- **数式ノードに被覆の数が現れたら赤くする。** 照合する箇所のブロックの数式ノードを走査し、
  4 つの数のいずれかが桁の境界つきで現れたら違反にする（`16` が `160` に当たらないようにしてある）。
  この判定は誤検出しうる（別の理由で同じ数が数式に出た場合）。**その誤検出は静かではなく赤い**ので、
  静かに空振りするより良い、という判断で採っている。

出力（現状）:

```
  本文が書いている被覆の数値: 2 箇所 / 4 文を台帳の実測値と突き合わせた
    期待: ロケール 2 件（ja / en）それぞれ 1 箇所以上、各箇所 1 文以上（根拠: 形式検証の到達点の段が
      日英とも被覆を数で述べている）。下回れば違反にする（0 件でも静かに緑になる道を塞ぐ）
    ja / paper_remark_formalization: 2 文 / 台帳の数を 1 ずつ動かして照合が動いた数 4 / 4
      （全数・完了・部分的・未着手）/ 数式ノードに現れた被覆の数 0 件
    en / paper_remark_formalization: 2 文 / 台帳の数を 1 ずつ動かして照合が動いた数 4 / 4
      （全数・完了・部分的・未着手）/ 数式ノードに現れた被覆の数 0 件
```

## 検出の実証

### 合成データによる検出テスト（毎回走る）

照合の本体を純関数へ切り出し、同じ関数へ合成データを流す検出テストを同じファイルに置いた
（`npm run test:formalization` ＝ `verify-formalization-coverage.ts --self-test`。`npm run check` に組み込んだ）。
8 件すべて期待どおりだった。

| 流したもの | 期待 | 結果 |
|---|---|---|
| 照合する箇所がロケールごとに 1 箇所も無い | 検出 | OK |
| 箇所は在るが照合する文が 0 文 | 検出 | OK |
| 照合する文字列が台帳の数に依っていない（数を動かしても同じ文字列） | 検出 | OK |
| 4 つのうち 1 つだけ照合から落ちている（未着手を述べていない） | 検出 | OK |
| 本文が数を数式ノードで書いている | 検出 | OK |
| 照合すべき文が本文から消えている | 検出 | OK |
| 現に本文が取っている形（4 つの数を地の文で述べる） | 通る | OK |
| 桁の境界（`160` / `245` を `16` / `24` と読まない） | 通る | OK |

### 本文を実際に書き換えた実証（一時的。元へ戻した）

合成データだけでは、本文の実物に対して効くことの証拠にならないので、本文を書き換えて確かめた。

1. **数を数式ノードで書き換えた**（日本語版の当該段落で `24` と `5` を数式ノードにした）
   → **違反 3 件で赤**。内訳は、照合すべき文が本文に無いこと 1 件と、
   数式ノードに全数（24）・完了（5）が現れていること 2 件。
   印字も `数式ノードに現れた被覆の数 2 件` に変わった。
   **cycle 28 の実装では、この形は「照合すべき文が無い」だけが出て、
   数が数式へ移ったという事実そのものは出なかった。**
2. **照合対象の文を本文から消した**（「本論文の主張 24 件のうち…未着手が 3 件である。」を削除）
   → **違反 6 件で赤**。内訳は、照合すべき 2 文が本文に無いこと 2 件と、
   4 つの数がいずれも固定されていないこと 4 件（照合が成り立っていないので固定の証拠が立たない）。
3. **どちらも元へ戻して緑に戻ることを確認した。** 戻した後の
   `git diff --stat -- content/ locales/` と `git status --porcelain -- content/ locales/` はどちらも空である。

## 自分が犯した誤り（記録）

- **固定の判定を、最初は「数を増やした文字列が本文に無いこと」だけで書いた。**
  照合すべき文がそもそも本文に無い状態（実証 2 の削除）でも「固定されている」と印字してしまい、
  実証の出力を読んで気づいた。増やす前の文が本文に在ることも要求する形へ直した。
  **検査を書いた直後に自分の出力を読んでいなければ、誤った緑を印字する検査を残していた。**
- **一時ファイルを `/tmp` へ置いた**（`/tmp/x`）。cycle 28 で他のエージェントと `/tmp` の名前が
  衝突した記録を読んでいたのに、rebase 後の確認で 1 回使った。以後は作業領域へ置く。

## 環境（本 step の内容ではないが、検証に必要だった）

`npm run check` の腐ったツール参照の検査（検査 R）は、mathlib の実ファイル
（`Mathlib/NumberTheory/MahlerMeasure.lean` など）が読めることを免除の根拠として確かめる。
新しい worktree には mathlib が無いため、最初の実行はこの 2 件で赤くなった
（本 step の変更とは無関係）。`lake exe cache get` で mathlib を入れてから再実行し、全段 exit 0 を得た。

## 残る限界

- **台帳が実態とずれる道は塞いでいない。** この検査が見るのは本文と台帳の一致だけである。
  形式化が進んだのに台帳を直していない場合、本文と台帳が一致したまま両方が古くなり、検査は緑のままである。
  台帳の状態（完了・部分的・未着手の判定）が正しいかは人の判断で、機械で確かめられない。
  この限界は検査の出力にも印字した。
- **数式ノードの判定は数字の一致しか見ない。** 被覆の数と同じ整数が別の理由で数式に現れれば誤検出する
  （走査するのは照合する箇所のブロックだけなので範囲は狭いが、原理的に残る）。
- **照合が固定しているのは「その 4 つの数が地の文に在ること」だけである。**
  本文がその数を正しい文脈で述べているか（たとえば「完了 5 件」を「未着手 5 件」と書いていないか）は
  文字列の一致では区別しているが、文そのものの言い換えに追随はできない
  （言い換えれば赤くなり、台帳側の組み立てを本文へ合わせて直すことになる）。
- **期待件数の根拠は本文の現在の形である。** 将来、被覆の数を述べる箇所を意図して増減させるときは、
  期待の根拠ごと書き換える必要がある（黙って期待を下げれば、その時点で検査は弱くなる）。
