|---|---|---|

## 何を「不在の主張」として拾ったか

拾う語は 漢字の「無い」「無く」「無し」、および「持っていない」「該当なし」「0 件」である。
実データを全数読んで決めた。拾った 22 箇所はすべて、素材・配線・こちらの設計の不在の主張だった。

**採らなかった拾い方と、その理由（すべて実データの反例）:**

- **平仮名の「ない」は採らない。** 台帳に 22 箇所あるが、その大半は
  「要らなかった」「使わない」「証明しない」「書いていない」で、素材の不在とは無関係である。
- **「存在しない」は採らない。** 実データでの用例は「閉形式が存在しないことの主張そのもの」
  （命題 C″ の (4)）で、これは形式化済みの非存在定理である。採ると、証明できた成果に
  実在確認のログを要求することになる。
- **「欠落」は採らない。** 実データでは「mathlib の欠落は … ではなく … である」
  「配線の欠落ではなく素材の欠落である」の形で、不在の主張の言い換えとして現れる。
  語そのものが向きを持たないので、主張の位置を指せない。

**拾ってから除いたもの（実データに現に在る誤検出）:**

過去の判定を鉤括弧で引用してすぐ否定している箇所を除いた。実データに 4 箇所ある
（「**step 1 の仕分けが「素材が無い」と判定したのは誤りだった**」など）。これは不在の主張ではなく
その撤回であり、除かないと **壁を撤回したエントリほど実在確認のログを要求される**という逆向きの
規律になる。判定は形で行い、鉤括弧の直後 30 文字以内に「誤り」「覆っ」「撤回」があるものだけを除く。
除いた件数は検査が毎回印字する（黙って捨てない）。

一度は採ろうとして落とした条件がひとつある。「不在の主張のうち mathlib に関するものだけを見る」ために
前後 80 文字に mathlib の語があるかを見る案を試したが、実データで 5 箇所が漏れた
（「整除の鎖は確かに無いが」「素材も無い——`Monsky` /」「`kirchhoff` 0 件・`matrixTree` 0 件」など、
主語が mathlib でも語が窓に入らない）。**漏れる向きが危ない側なので採らなかった。**

## 何を根拠と認めたか

1. 実在確認ログのパス `lean/logs/*.log`。
2. 走査の実測値、すなわち 日付・mathlib のコミット・走査ファイル数の 3 つが揃っていること。

`lean/README.md の欠落調査` のような**文書への指し示しは認めない**。
指し示された先が現在どの mathlib を見た結果なのかを機械が辿れないためである。
現に台帳の 1 エントリ（命題 G）がこの形だった。

粒度は **主張は箇所ごとに拾い、根拠はエントリ単位で見る**。箇所ごとに要求しないのは、
台帳が「主張の文で括弧を開き、2 文あとで閉じる」形で根拠を書いており、文で切ると根拠と主張が
別々の断片へ落ちるためである（命題 LSW の欄で確認した）。
代償として、同じエントリ内の別の主張が無関係なログで通る。これは保証しない。

## 検査（検査 F の中で回す。段は増やしていない）

`npm run check` の段数は 29 のままである。段を増やさなかったのは、主題が同じ台帳
（形式化の被覆）の健全性であり、検査 F がすでに台帳を読み込んで走っているためである。
段を分けると、同じ台帳を 2 度読んで別々に赤くなる状態を作ることになる。

確かめること:

- 不在の主張を含むエントリが根拠を持つこと（持たなければ違反）。
- 根拠に挙げたログが実在すること（実在しなければ違反）。
- ログが mathlib のコミットを記録していること（記録が無ければ違反）。
- ログが記録している mathlib のコミットと、`lean/lake-manifest.json` が指す現在のコミットを印字し、
  違えば「古い」と数えること。

**コミットの不一致を違反にしなかった理由。** mathlib はこちらの都合と無関係に進むので、
不一致を違反にすると mathlib を上げた瞬間に根拠つきのエントリが全件同時に赤くなる。
赤を消すには走査をやり直すしかないが、走査には mathlib を展開した `lean/` が要る一方、
`npm run check` は mathlib 不在でも通ることを前提に組んである。
通せない検査は、いずれ「落ちているのが普通」になって効かなくなる。
古いログを黙って根拠にし続けられないようにするのが目的なので、件数として毎回見えれば足りる。
違反にするのは、ログの実在とコミットの記録という、こちらの手の内にあるものに限った。

## 直した 6 エントリ（免除表へは 1 件も入れていない）

6 件のうち 5 件は、**すでに存在するログが実際にその概念を走っていた**ので、
ログのパスと実測値（日付・コミット・走査ファイル数・当たった件数）を台帳へ足した。
足す前に、そのログの該当箇所を開いて中身を確認している。

- 命題 N → `lean/logs/mathlib-gap-survey-cycle29.log`（`SkolemMahlerLech` 0 件・`Strassmann` 3 段とも 0 件・
  `NewtonPolytope` 3 段とも 0 件）。
- 命題 F → `mathlib-gap-survey-cycle29-duality.log` の「d 変数の完備群環」の段

**残る 1 件は完全には直っていない。** 命題 C′ の欄が書いていた

## 限界

- **根拠の中身が主張に合っているかは機械が見ない。** ログが実在し、どの mathlib を見たかが
  記録されていることまでしか確かめない。挙げたログがその概念を実際に走っているかは人が見る
  （本 step は 5 件すべて開いて確認したが、それは検査の保証ではない）。
- **粒度がエントリ単位である。** 同じエントリの中の別の不在の主張が、無関係なログで通る。
- **走査の実測値は 3 要素が同じエントリに在ることしか見ない。** その日付・コミット・ファイル数が
  同じ走査のものかは確かめられない。
- **ログのパスは ASCII の名前しか拾わない**（現存するログはすべて ASCII）。
- **「不在の主張」の判定は字面である。** 新しい言い回し（「見当たらない」「用意されていない」等）で
  書けば、この検査は素通りする。拾う語は実データから決めており、原理から出たものではない。
- **こちらの未設計についての不在**（「型にする設計をこちらが持っていない」「配線が無い」）も
  同じ規律で拾っている。mathlib のログでは埋まらない種類の不在なので、
  実データではいずれも mathlib についての主張を併せ持つエントリにしか現れていないが、
  それだけの主張を書いたエントリが将来現れたら、この検査は根拠を要求して過検出になる。
