# cycle 28 step 6: 本文が書いている被覆の数値を、台帳の実測値と突き合わせる検査にした

変更: `structured-latex/tools/{formalization-coverage,verify-formalization-coverage}.ts`。

## 何が問題だったか

本文（形式検証の到達点）は被覆を数で述べている——「本論文の主張 24 件のうち、
内容が形式化されているのは 5 件、一部が形式化されているのは 16 件、未着手が 3 件である」。
**形式化が進めばこの数は古くなるが、古くなったことは本文を読まないと分からない。**
cycle 27 step 7 はこれを限界として記録し、cycle 28 へ送っていた。

実際、**本サイクル step 1 でこの数はすぐ古くなった**（部分的 14 → 16、未着手 5 → 3）。
そのときは step 1 が本文も一緒に直したが、**直し忘れても誰も気づかない**状態だった。

## 選んだ形

state ファイルは「検査にするか、本文から数を落として台帳を指すか」の 2 択を挙げていた。
**検査にするほうを採った。** 理由は、本論文が自分の到達点を数で述べることは読者に対する
誠実さの一部であり（全数形式化が目標だと書いている以上、いまどこかを数で示す義務がある）、
落とすと読者は `lean/README.md` を開かないと分からなくなるからである。

## どう実装したか

**数の出どころを台帳ひとつにした。** 台帳（`FORMALIZATION_COVERAGE`）から
完了・部分的・未着手を数え、その実測値を入れた文字列が本文に実在することを確かめる。

```
本論文の主張 24 件のうち、内容が形式化されているのは 5 件、
一部が形式化されているのは 16 件、未着手が 3 件である。
```

日英それぞれについて、この 2 文（英語も 2 文）を組み立てて照合する。
**数だけ直して検査を通す道は無い**——数が台帳から出ているので、
本文を直すには台帳を直すしかなく、台帳は実態と紐づいている（宣言が浮けば別の検査が赤くなる）。

本文を**言い換えたときも赤くなる**。そのときは組み立て方（`COVERAGE_NUMBER_SITES`）を
本文へ合わせて直す。言い換えを黙って許すと、照合の空振りに気づけないからである。

## 検出の実証

本文の「16 件」を「14 件」に書き換えて走らせ、**違反 1 件で落ちること**を確かめた
（`[本文の被覆の数値が台帳と合わない] ja / paper_remark_formalization — 本文に「…」が無い
（台帳の実測: 全 24・完了 5・部分的 16・未着手 3）`）。書き戻して違反 0 件に戻ることも確かめた。

## 検証

`npm run check`（28 段）exit 0、`build:pdf` 日 50 頁・英 64 頁。

## 限界

- 照合しているのは**地の文の文字列**である。本文が数を数式ノードで書くようになれば
  （`$24$` 等）、照合は空振りする。いまは 0 件だが、**空振りしても静かなまま**である。
- 台帳の状態語（完了・部分的・未着手）が実態と合っているかは、この検査では確かめられない。
  **「完了」が本当に完了かは人の判断である**という検査 F の限界はそのまま残る。
  本 step が塞いだのは「台帳と本文がずれる」道だけであって、「台帳が実態とずれる」道ではない。
