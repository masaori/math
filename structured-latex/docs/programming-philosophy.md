# プログラミング哲学

## AI時代のプログラミング戦略

AIによって低コストに高品質なコードが生成されるようになった。しかし、以下のファクトにより、**厳密な依存関係コントロール**・**曖昧さの排除されたアーキテクチャ**・**プログラムによるコード自動生成**が今まで以上に重要であることが浮き彫りになった時代だと言える。

### AIと人類の共通点：確率的に振る舞う

- AIも人間も確率的に振る舞う。どちらも一定のエラー可能性があり、これが0になることはない。
- 高品質に一見見えるコードだとしても、エラーは指数関数的に累積し、必ずどこかで爆発する。

### AIと人類の違い：認知能力の飛躍的増加

- AIの登場により認知能力が飛躍的に増加した。
- これにより、より複雑なルール設計であっても「厳密性」さえ担保されていれば運用が可能になった。

### 結論：エントロピーの最小化

以上から言えることは、一つ一つの作業に対しての **「エントロピー = 選択肢の多さ」をいかに小さくするか** が最も重要だという点である。

このことを最優先したルール・アーキテクチャを敷く。

---

## 具体戦術

以下の4つの戦術は互いに依存し合い、それぞれの目的を高め合っている。

### 1. 原理主義的なDDD

本来DDDはユーザーのメンタルモデルをプログラムが理解できる形で記述し、それをソースコードに適用し続けることが本懐であった。これを厳密なルール・アーキテクチャ設計と自動生成によって、より一層促進する。

さらに、UI設計の思想としてOOUI（オブジェクト指向UI）設計を導入することで、domain-modelの表現を中心としたUI設計が可能となる。ドメインモデルがバックエンドからフロントエンドのUI構造まで一貫して貫かれることで、DDDの本懐がシステム全体で実現される。

### 2. カスタマイズされたクリーンアーキテクチャ / FSD の厳密な運用

- どちらのアーキテクチャも「依存関係のコントロール」を主眼としている。
- 関心の境界を常に「ドメイン知識」と「インフラ知識」によって厳密に定める。

### 3. できるだけ多くのコードを自動生成する

- 自動生成されたコードは理論上エントロピーが0である。
- 「自動生成コードの組み合わせ」として作業設計することにより、作業全体のエントロピーを最小化する。
- domain-model の表現を Entity-Relation とすることにより、シンプルな CRUD / RESTful API についてはほぼ自動生成できる。
- 特定のAPIについてのみの実装要件が出てきた場合は、**必ず**一度立ち止まり、自動生成スクリプトに敷衍することが可能ではないか考え、できるだけ全ての共通仕様とするべき。
- 最適化等を後で行う場合は、自動生成を切り分ける設定を設計するか、wrapした手書きコードを実装することで、エントロピーの増加せざるを得ない箇所を最小限に止めるよう努力する。

### 4. ユーザーファーストなエラーハンドリング

- エラーは「ユーザーの操作に影響がある事象」であり、伝える必要のないエラーは存在しない。
- エラーハンドリングの起点は「ユーザーにどう伝えるか」であり、技術的な都合ではない。
- 型システムによってエラーの存在を可視化し、処理漏れをコンパイル時に防ぐ。
- **エラーに関わるコードを書く際は、必ず[エラーハンドリング戦略](./error-handling-strategy.md)を参照すること。**
