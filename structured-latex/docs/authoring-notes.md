# 書き方の注意（利用側が踏む落とし穴と、その避け方）

このシステムを使って文書を書くとき、また文書を機械的に書き換えるときに、実際に踏んだ
落とし穴と、その回避手順をここに集める。**設計判断ではなく、利用側の手順の正本**である
（設計の根拠は [domain-model.md](domain-model.md)、型と実行時検査の切り分けは
[type-coverage.md](type-coverage.md)）。

各項目には、**どこで踏んだか（プロジェクトと日付）**を残す。再発したときに、同じ話か
別の話かを判定できるようにするためである。

## 大きな文書は、章ごとに型を確定させる

**症状。** 本文全体を 1 つのリテラルとして `defineDocumentStructure` に渡すと、TypeScript が
構造の比較を最後までやりきれず、**実在しない不一致**を報告する。典型的には、グループの
`beforeFocus` 配列の 2 番目の要素が 1 番目の要素の型に一致しない、という成り立ちようのない
エラーになる（配列の要素型が先頭要素の型に固定されたかのように振る舞う）。

**判別のしかた。** 章ごとに切り出して 1 章ずつ型検査すると、どの章も 0 件で通る。
まとめたときだけ落ちるなら、この症状である。入力そのものは正しい。

**避け方。** 章 1 つを `defineSection(...)` に渡して型を確定させ、`content/*.ts` の
default export はその**章の配列**にする。生成器は構造を直接読み、型検査では
`BlocksOfSections` が同じ順序のタプルへ平坦化するので、大域的な ID・ラベルの一意性検査は
そのまま効く。

**やってはいけないこと。** 章ごとに確定させたあと、それらを `defineDocumentStructure` で
束ね直すこと。束ね直した時点で文書全体が 1 つのリテラルとして再比較され、同じ症状が出る。
束ねるのは読み込み側（生成器・出力器）の仕事である。

## default export をタプルのままにする

`BlocksOfSections` / `BlocksOfDocumentStructure` がブロック ID・ラベルの一意性を検査できるのは、
default export が**タプル型**のときだけである。配列型（`Section[]`）に広がると、平坦化の結果が
空タプルになり、「生成済みラベルと本文が一致すること」の検査が黙って通ってしまう。

したがって、章定数を並べた配列には `as const` を付ける。また、`content/*.ts` の中で
`compileDocumentStructure` を呼んで**その結果を default export しない**（結果は配列型なので
同じ理由で検査が効かなくなる）。

## ブロックを名前付き定数へ切り出さない

ブロックのリテラルを `const d1 = { ... }` のように切り出すと、`paragraph([...])` などの
ノード構築子が**文脈型を失う**。ラベルのユニオン型が伝わらず `ParagraphNode<string>` になり、
そのブロックを木へ入れた時点で型エラーになる。ブロックは木の中に直接書くか、
`defineElementGroup` / `defineSection` を通して文脈型を与える。

## 木を機械的に書き換えるときは、テンプレートリテラルの中の行に触れない

**症状。** 字下げを揃えるために各行の行頭を削る処理を書くと、複数行にまたがる
`` String.raw`...` `` の**中の行**まで削ってしまう。数式の行頭にある `\begin{cases}` が
`egin{cases}` に、`\kappa` が `appa` になる。**バックスラッシュが消えるだけなので、
見た目ではまず気付かない。**

**避け方。** 行を書き換える処理では、バックティックの開閉を数えてテンプレートリテラルの
内側かどうかを判定し、内側の行は 1 文字も変更しない。

**確認のしかた。** 書き換えの前後で、ソース中の `` String.raw`...` `` の中身を全件取り出して
突き合わせる。件数と内容が完全に一致することを確認してから次へ進む。数式は目視では
検査できないので、この突き合わせを省略しない。

- 踏んだ場所: 同上（13036 件の数式のうち数十件を壊し、突き合わせで検出した）

## 記号を増やす前に、その記号が空いているか調べる

1 つの記号は 1 つの意味に固定する規律を守るには、**新しい記号を導入する前に、その文字が
文書のどこかで既に使われていないかを調べる**必要がある。実際に、列ベクトルの全体と
格子の頂点集合が、どちらも $V_L$ という同じ記号を持っていた事故がある。

調べ方は、ソース中の `` String.raw`...` `` の中身だけを取り出し、その文字が
独立したトークンとして現れる箇所を数えることである（散文やコメントを一緒に検索すると
`String.raw` 自体の `R` のような偽陽性で埋まる）。

- 踏んだ場所: 同上（$V_L$ の衝突。添字集合を一般化する際に解消した）

## 数式中の変数名を機械的に置き換えたら、直前の制御綴と癒着していないか調べる

**症状。** `\tau` を `u` へ一括で置き換えると、`\ne\tau` が `\neu` になる。TeX から見ると
これは「未定義の制御綴 `\neu`」であり、**組版の段階で初めて落ちる**。構造化テキストの検査は
数式の中身を TeX として解釈しないので、ここでは捕まらない。

**避け方。** 置き換えたあと、変更した範囲で `\<英字の並び><新しい変数名>` の形を検索し、
現れた制御綴が実在するものかを確かめる。癒着していたら空白を 1 つ入れる（`\ne u`）。
置き換える変数名がバックスラッシュで始まらない場合（`R_L` → `\mathcal{J}` など）は
この問題は起きない。**バックスラッシュで始まる名前を、始まらない名前へ変えるときだけ**起きる。

**確認のしかた。** PDF を実際に組む。構造化テキストの検査と型検査だけでは検出できない。
