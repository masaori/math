# 何を型で落とし、何を実行時に残すか

入力言語の誤りは、**できる限りコンパイル時（`tsc`）に落とす**方針である。
このメモは「いま何が型で落ちるか」と「型で落とせないものは**なぜ**落とせないか」を、
実際に型を書いて確かめた結果とともに記録する。**憶測ではなく、下記はすべて実測に基づく。**

対応する実証テスト: `tools/negative-type-test.ts`（誤った入力で `tsc` が実際に落ちること、
および**正しい入力では落ちないこと**を対で確認する。16 ケース × 2）。
対で回すのは、「設定不備で常に落ちているだけ」を正常と誤認しないためである。

不変条件の番号（I1–I5）は [domain-model.md](./domain-model.md) §5.2 に対応する。

## 1. 型で落ちるもの（コンパイル時）

| 検査項目 | 対応する不変条件 | 仕組み | 誤ったときの診断 |
|---|---|---|---|
| `ref()` が存在しないラベルを指す | I2 | `ref(target: L)`。`L` は content から生成したユニオン型 | 近い綴りの候補付き（TS2820） |
| ノートの `targets` が存在しないラベルを指す | I2 | `targets: readonly [L, ...L[]]` | 同上 |
| ノートの `targets` が空 | I2 | 1 件以上を要求するタプル型 | `Source has 0 element(s) but target requires 1` |
| ブロックが未登録のラベルを宣言 | I1 | `labels: readonly L[]`（＝生成物の再生成漏れを検出） | TS2820 |
| **同一ファイル内**のブロック id 重複 | I1 | `defineBlocks` の `const` 型引数 ＋ 重複検出型 | `__ブロックidが重複している: "<id>"` |
| **同一ファイル内**のラベル重複 | I1 | 同上 | `__ラベルが重複している: "<label>"` |
| **同一ファイル内**のノート id 重複 | I1 | `defineNotes` の同種の型 | `__ノートidが重複している: "<id>"` |
| **ファイルを跨いだ** id / ラベル / ノート id の重複 | I1 | 生成された `document.generated.ts`（全ファイルを import して 1 本のタプルへ連結し、重複を `never` 制約で拒否） | `does not satisfy the constraint 'never'` |
| ノート id とブロック id の衝突 | I1 | 同上（両者を連結して重複判定） | 同上 |
| 文書が空 | I3 | 同上（`_ContentIsNotEmpty`） | 同上 |
| 見出しが本文（`statement` / `proof`）を持つ | I4 | `HeadingBlock` の `statement?: never` | TS2322 |
| 定理型が見出し専用の `level` を持つ | I4 | `TheoremLikeBlock` の `level?: never` | TS2322 |
| 図表が定理型のフィールドを持つ | I4 | `FigureBlock` の `statement?: never` ほか | TS2322 |
| 見出しの `level` が 1〜6 の範囲外 | I4 | `HeadingLevel = 1｜…｜6` | TS2322 |
| タイトルが `text` も `tex` も持たない | I4 | 「少なくとも一方が必須」の union | TS2322 |
| 本文ブロックが `notes` を持つ | I5 | `notes?: never`（ノート混入の入口を型で塞ぐ） | TS2322 |
| フィールド名の打ち間違い（`proof` → `proofs`） | — | 余剰プロパティ検査 | `Did you mean to write 'proof'?` |
| プロジェクト固有メタデータの条件違反（例: 非可算を宣言したのに脱出箇所が無い） | — | 判別共用体で受けたメタデータ `M` | TS2322 |
| 生成済みラベル一覧が content とずれている（両方向） | I1 | `document.generated.ts` の `Exclude` 主張 | `does not satisfy the constraint 'never'` |

### 実装上の要点（同じ轍を踏まないために）

- **`const` 型引数だけでは余剰プロパティ検査が効かなくなる。** 先行実装の実測: `defineBlocks<const T>(b: T)`
  の形にすると `proofs:` の打ち間違いが素通りした。`b: T & readonly Block<L, M>[]` と
  **具体型との交差**にすると、リテラル型の推論（重複検出に必要）と余剰プロパティ検査が両立する。
- **重複検出の再帰型は末尾再帰で書く。** 素朴な `[...H['labels'], ...LabelsOf<R>]` は 173 ブロック
  規模で TS2589（Type instantiation is excessively deep）になる。このとき `tsc` 自体は落ちるが、
  **診断が TS2589 に化けて「重複がある」という指摘は出なくなる**——つまり検査として役に立たなくなる。
  累積引数を持つ末尾再帰形にすると通る。**TS2589 が出たら「検査が壊れた」と読むこと。**
- **再帰の限界は実測で約 900 要素**（先行実装での測定。100/200/400/800/900 は検出、1000 以降は不可）。
  これを超える文書が出たら、章ごとに分割して部分結果を合成する形へ変える。
- **一意性ユーティリティの制約に `Block<L, M>` を使わない。** `Block<string, never>` のような具体化で
  交差が潰れる（`X & never = never`）ため、制約として機能しなくなる。`{ id; labels }` という
  最小の形（`Identified`）だけを要求する。
- **生成した集約モジュールを型検査の対象から外すと、検査は静かに消える。** 先行実装で実際に起きた事故。
  生成器は、プロジェクトに `tsconfig.json` があれば生成物 2 種が `include` に書かれていることを検査する。
- **制約の無い「主張」は何も検査しない。** `export type X = A extends B ? true : never` は条件が偽でも
  `never` という別名が定義されるだけでエラーにならない。`Assert<T extends true>` のように
  **制約**の形にして初めて落ちる。

## 2. 型では落とせないもの（実行時検査として残す）

### 2.1 型を経由せずに作られた値

外部から受け取った JSON（アップロード）、`as` で型検査を迂回した値、動的生成した値は、当然ながら
型では守られない。`domain-model/structured-text/validate.ts`（Zod・Result）がこの経路の唯一の関門で、
**ブロック 1 件の形**（I4・未知フィールド・ノード種別）を見る。

- `.strict()` により、**宣言していないキーは拒否される**。プロジェクト固有メタデータのキーは
  ファクトリへ渡した宣言だけが許可キーに加わる。
- ただし**語彙を所有しない読み手**（どのプロジェクトの文書でも読む汎用ビューア等）は
  `unknownBlockMeta: 'passthrough'` を使う。キー名を知りようがない立場で未知キーを拒否しても
  打ち間違いの検出にはならず、正しい文書を読めなくするだけだからである。この場合も
  **値は落とさない**（strip すると画面に出す前にメタデータが黙って消える）。既定は `reject` 側で、
  「検査が緩いほうが既定」にはしない。
- **エラーは 1 件目で止めずに全件返す**（受け取り側が一度で直せるように）。
- `.parse()` は使わない（throw するため）。`.safeParse()` の結果を Result に変換する。

### 2.2 文書全体にかかる不変条件（アップロード経路）

型で落ちるのは「著者が TypeScript で書いた文書」だけである。アップロードで受け取った文書には
生成物（ラベルのユニオン型・集約モジュール）が存在しないので、I1–I3 は実行時に判定するしかない。
これを担うのが `resolve` で、**同じ判定を 2 か所に書かない**ために検証専用の関数を別に置いていない
（未解決参照・重複・空文書はすべて `ResolveError` として返る）。

### 2.3 数式が LaTeX と KaTeX の共通部分集合であること（D-1）

**型で書けないのは制約ではなく、入力がリテラル型でないことが原因。**
テンプレートリテラル型で「特定の部分文字列を含む文字列を拒む」制約は書ける（先行実装で実測）。
ところが数式は `String.raw` タグ付きテンプレートで書かれ、**その戻り値型は `string`（リテラル型ではない）**
であるため、制約が効かない。自前のタグ付きテンプレート関数でも `TemplateStringsArray` の `raw` は
要素型が `string` に潰れるので、`const` 型引数を付けてもリテラルは得られない（実測済み）。
→ **生成段の機械検査として実装する（M3）。**

### 2.4 資産（`assetKey`）が実在すること

型システムはファイルシステムもオブジェクトストレージも参照できない。
`assetKey` から実体への解決はターゲットごとに違う（LaTeX はビルドディレクトリ相対、Web は配信 URL）。
→ 出力器へ渡す資産解決器が、解決できない `assetKey` を**エラーにする**（黙って落とさない）。M5 / M7。

### 2.5 生成物とファイル一覧の一致

`document.generated.ts` は「列挙されたファイル」の中身については型で保証するが、
**ディレクトリに増えたファイルが列挙から漏れている**ことは型では検出できない
（型システムはディレクトリを列挙できない）。
→ `codegen/structured-text-index/cli.ts --check` が、生成し直した結果と現物の一致を検査する
（`npm run check` の最初のステップ）。ER 定義側も同じ形で `--check` を持つ。

### 2.6 依存方向

import の向きは型では表現できない（どのファイルからでも import できてしまう）。
→ `tools/check-dependency-direction.ts` が実際の import を読んで検査する。
`domain-model/` は他の層にも Node の組み込みモジュールにも依存してはならない（純粋に保つ）。

## 3. 検査の回し方

```sh
cd structured-latex
pnpm install      # 初回のみ
npm run check     # ER 定義の鮮度 → 生成物の鮮度 → 型検査 → 依存方向 → 単体テスト → 負テスト
```

ラベル・ブロックを増減したら `npm run gen:example`（プロジェクト側なら
`node <system>/codegen/structured-text-index/cli.ts --project <dir>`）で生成物を作り直す。
忘れると型検査が落ちるので、取りこぼしにはならない。
