# 証明の積み上げの runbook

連続実行「クリフォード代数の同型: 証明の積み上げ」が、毎回この手順で台帳の一行（一つの節）を書き切る。
進捗の正本は [状態台帳](proof-state.md)、章立てと証明の経路の正本は [構成案](structure-proposal.md) である。
方向性と台帳の順序は、毎日の研究管理の定時実行が決める。積み上げの実行は方向性を変えない。

## 毎回の手順

1. **同期。** `git fetch origin && git rebase origin/main` で作業ツリーを main の最新にする。
2. **読む。** リポジトリ直下の CLAUDE.md・AGENTS.md・`docs/context/` の全ファイル、このプロジェクトの README・MEMORY・
   構成案・状態台帳。
3. **前進。** 状態台帳の「次の一歩」の表で、状態が「未着手」の最初の行を、括弧の中のブロックを全部書くまで行う。
   書いている途中で補題が要ると分かったら、同じ行の中で書き足す。台帳に行を足さない。
   先頭が判断待ちで進められなければ、次に実行できる行へ進み、そのことを台帳の「前進の記録」に一行残す。
4. **書く。** 定義・主張・証明を `structured-latex/content/chapters/` の該当の章のファイルに足す。
   章のファイルは、構成案の章ごとに一つ置く（`mathematical-toolkit.ts`・`complex-matrix-algebra.ts`・`clifford-algebra.ts`・
   `isomorphism.ts`）。ファイル名に番号を付けない。章のファイルを新しく作ったら、`structured-latex/content/main-text.ts` の配列の、
   構成案の章立てどおりの位置に足す（数学的道具立て → 複素行列環 → クリフォード代数 → 同型の証明）。
   `content/` 直下に章のファイルを置かない。システムは `content/` 直下のファイル名の辞書順を文書順にするので、章の順が化ける。
   台帳の実行順は文書順と一致しない。台帳の行がどの章に属するかは、台帳の「章」の列で決める。
5. **SageMath。** 行列の計算を含む行は、`sagemath/check/<対象名>/` に検算を置き、`overview.md` に対象ラベルと結果を書く。
   厳密計算（`ZZ`・`QQ`・`QQbar`）で行う。抽象的な代数の中の等式（クリフォード代数の中の計算）は、
   行列への像で確かめたことを、像での確認であると明記して書く。証明の代わりにしない。
   SageMath 10.9 は VM の micromamba の環境 `sage` に在り、PATH には無い。`which sage` で見つからなくても無いと判断せず、
   `micromamba run -n sage sage sagemath/check/<対象名>/<ファイル>.sage` で実行する。python3 で代用しない。
6. **検証。** `(cd structured-latex && npm run gen && npm run check && npm run build:pdf)` を通す（build:pdf は最終成果物の PDF に組めない文字・未解決参照が無いことを確かめる。tectonic が無い環境ではそのことを前進の記録に書く）。SageMath の検算を置いた行は実行して結果を書く。
   落ちたら本文を直す。検証を主張に合わせて緩めない。
7. **台帳と MEMORY の更新。** 台帳の行の状態（記述・SageMath・Lean のどこまで済んだか）と、前進の記録を書く。MEMORY の「次回やること」を直す。
8. **main へ入れる。** `git fetch origin && git rebase origin/main` の後に main へ push し、
   `git merge-base --is-ancestor HEAD origin/main` で包含を確かめてから終える。研究管理の実行が同じ時間帯に main を更新するので、
   衝突したら相手の変更を残して解消する。
9. **止まる。** 一行を書き切ったら終える。Slack へは報告しない。論文の公開もしない（研究管理が行う）。

## 一回の作業の大きさ

- **台帳の一行は一つの節とする。** 節とは、下流の主張から引かれる一つの結果（例: テンソル代数の普遍性）と、
  それを示すのに要る定義・補題のまとまりである。一回の実行で一行を書き切り、30分から1時間程度の作業になる大きさにする。
- **行を一つの定義・一つの主張の単位へ割らない。** 研究管理も割らない。
  2026-11-11 までの台帳は一行を一つの定義・主張にしていたため、一回の実行の作業が平均3.5分で終わり、
  実行の間の120分の大半が進まなかった。
- 本文の「1 ブロック 1 主張」（`docs/context/証明の書き方.md`）は変えない。一つの行の中で、定義・主張ごとにブロックを分けて書く。
  証明が式変形の長い連なりになる主張は、同じ行の中で補題のブロックに割る。
- 一回の実行で書き切れなかったら、書き終えたブロックまでを main へ入れ、その行に「（済んだブロック: …）」を書き足して、
  状態は未着手のまま終える。次の回が同じ行の続きを書く。

## 書くときの注意

- **同一視をしない**（README の「記述の規約」）。写像に名前を付け、その写像を通してだけ行き来する。
- 本文で証明済みのブロックを使う行には、必ずラベル参照を付ける。
- 主張に必要な条件（well-defined 性、商代数への写像が代表の取り方によらないこと等）は本文に書く。ノートに逃がさない。
- 直和 $`W\oplus W^{*}`$ の元は組である。$`W`$ や $`W^{*}`$ の元を直和の元として使うときは、台帳の「直和の成分への埋め込み写像」で名前を付けた写像を必ず通す（$`\gamma(w_i)`$ と書かない）。
- 番号の付いていない有限集合（部分集合全体 $`\mathcal{P}_M`$、行列の添字集合など）の上の和は、台帳の「番号の付いていない有限集合の上の和」の行が済んでから、その定義をラベル参照で引いて使う。線型結合（番号順の和）で代用しない。
- 主定理と構成案の系の証明で引かない主張は足さない（`docs/context/証明の書き方.md` の「新しい道具を入れるときの判断」）。行を割るときも、割った先の主張が下流で引かれるかを確かめる。
- 有限集合の元の個数（$`\#T`$）と、部分集合の元を小さい順に並べる写像は定義しない（番号付けの長さが一つに決まることを本文で示していないため）。符号 $`(-1)^{\#\{t\in T:t<i\}}`$ は台帳の「個数 N_i(T) の定義」で、$`a^{\dagger}_S`$ は $`t=1,\dots,M`$ の順の積で書く。
- 写像（$`V\to\mathrm{Mat}`$ の線型写像、$`\Psi`$）は、座標の写像や行列の成分を使った式で直接定める。「基底での値から線型写像へ延ばす」補題を経由しない。式で書けば well-defined 性の議論が要らない。
- 証明の末尾に「この議論は〜の条件を使わない」と、使わなかった仮定を並べない。どの仮定が要らないかは Lean の必要十分版で見る（`docs/context/証明の書き方.md` の「必要十分版は Lean の中だけに置く」）。人手証明では正しさに要らない文で、式変形の読み手の注意を散らす。
- k 重テンソル積の存在は、V の基底 b_1..b_n の座標で、有限集合 {1..k}→{1..n} の上の ℂ 値写像の空間として構成する。V の元の組の上の自由線型空間と、線型空間の部分空間による商は使わない（この論文のどの V も有限の基底をもつため）。
- 添字・個数・番号付けに使う整数（ℕ・ℤ）の加減・積・冪・順序には、属する構造の添字を付けない。README の「演算と単位元には、属する構造を添字で書く」は、代数・環・線型空間の演算についての規約である。ℂ の中の演算には添字を付ける。
- 引いた主張の束縛変数へ代入するとき（「f:=γ∘in_1」など）は、そのブロックで既に別の意味をもつ文字（双対基底 f、二次形式 q、基底 w など）を使わない。
- 定義のブロックの中で等式や性質を主張しない（「m=M なら全体に一致する」「漸化式を満たす」など）。主張は別の主張のブロックに置き、引く側はそのラベルを引く。補助の記号（因子の族など）を他のブロックが引くなら、その記号も別の定義のブロックにする。
- 根拠の違う等号を地の文の一行につながない（「A=B=C」）。二つ以上の等号は整列した式変形にして、行ごとに根拠を書く。
- 採らなかった経路は捨てず、`structured-latex/notes/` に理由と一緒に置く。

## Lean

主定理まで記述と SageMath が揃ったので着手してよいが、台帳の順序に従い、主定理の系の記述を先に済ませる。Lean の具体版は本文と 1 対 1 に対応させるので、系の記述で数学的道具立てに補題が増えても、Lean を書き直さずに済む。`lean/` の設定は、
`exact-solution-of-2d-ising-model/lean/README.md` の具体版・必要十分版の規約に合わせて、その段で作る。
時間のかかる処理（`lake update`・`lake build`）は前面で実行し、終わるまで待つ。裏で走らせたまま終えると成果が残らない。

- **版を揃える。** `lean-toolchain` と mathlib の版は `exact-solution-of-2d-ising-model/lean/` と同じにし、`lake exe cache get` でビルド済みのキャッシュを使う。
- **具体版は、本文が自分で定義した構造を、本文の定義どおりに Lean の structure と def で書く。** 環・ℂ-線型空間・線型写像・有限集合の上の和・ℂ-代数・
  両側イデアルと商代数・k 重テンソル積・テンソル代数・二次形式・クリフォード代数・行列環 Mat_S(ℂ) がこれに当たる。
  mathlib の `Module`・`Algebra`・`TensorProduct`・`DirectSum`・`CliffordAlgebra`・`Matrix` の一般論で置き換えない。置き換えると、本文の証明と 1 対 1 にならない。
  ℂ の四則と、その計算の自動化（`ring`・`simp`・`norm_num`）は使ってよい。本文も ℂ の四則を既知として使っている。
- **必要十分版は、具体版と同じ structure と同じ手順のまま、ℂ を型の変数に替え、証明が実際に使う係数の性質だけを仮定する。**
  削れなかった仮定（2 の可逆性、平方根の存在など）は、どの主張で要るかをコメントに書く。具体版は必要十分版の特殊化として導く（`docs/context/証明の書き方.md` の「Lean 必要十分版」）。
- **各定理の docstring に、対応する本文のラベルを書く。** 一つの行で、その節の本文のブロックを全部形式化する。
- Lean の行の検証は、`lake build` と、`sorry` が残っていないことの検査である。本文を直したら `npm run check` も通す。
- Lean で本文の誤りや、本文が書いていない前提が見つかったら、本文を直す（同じ行の中で）。主張が偽なら、台帳の「研究管理への申し送り」に書いて止まる。

## 止まってよい場合

- `docs/context/` の変更が要ると分かったとき。変えずに、変更案を台帳の「研究管理への申し送り」に書いて終える。
- 証明の経路そのものが成り立たないと分かったとき。反例や行き詰まりを台帳の「研究管理への申し送り」に書いて終える。
