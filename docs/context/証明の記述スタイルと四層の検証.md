# 証明の記述スタイルと四層の検証

**全プロジェクト共通の記述哲学。** 正本はこのファイルとする
（従来 `exact-solution-of-2d-ising-model/README.md` にプロジェクト固有として書かれていたものを、
リポジトリ全体の方針へ昇格させたもの。Ising プロジェクト固有の**道具立ての制限**——
リー群を使わない、テンソル積はクロネッカー積で書く等——は引き続きそちらの README を正本とする）。

## 中心テーゼ

> **証明は「人が一行ずつ追えること」と「機械が検査できること」を同時に満たす。**
> どちらか一方しか満たさない証明は、このリポジトリでは未完成とみなす。

厳密だが読めない証明は失敗である。読めるが機械検査できない証明も、
[基本方針_可算コアとℝ脱出](基本方針_可算コアとℝ脱出.md) の中心テーゼ（可算＝決定可能＝機械可読）に照らして未完成である。

そのために**四つの層**を積む。上の層が下の層を検査する。

| 層 | 何をするか | 何を保証するか | 置き場所 |
|---|---|---|---|
| **「記述」層** | 1 ステップ 1 定理で書き、各行に根拠を添える | 人が追える。省略に嘘が隠れない | `structured-latex/content/` |
| **「SageMath 検証」層** | 式変形を **1 行ずつ** SageMath で確認する | 書き間違い・符号ミスが残らない | `sagemath/check/<対象名>/` |
| **「Lean 具体版」層** | 人手証明と **1 対 1 に対応する** Lean 証明 | 人手証明そのものが正しい | `lean/<Lib>/<章名>/` |
| **「Lean 必要十分版」層** | 同じ手順のまま抽象度だけ必要十分まで上げた Lean 証明 | **何が本質的か**が分かる。具体版が過剰な構造を要求していないかの検査 | `lean/<Lib>/NecSuf/` |

**「Lean 必要十分版」層は「抽象化」ではなく「必要十分性の見極め」である。** 名前に注意すること（「層をまたぐ規約」節）。

## 「記述」層 — 記述のルール

### 一ステップ一定理（最重要）

- **式変形を絶対に省略しない。** 移項・素朴な四則演算も含め、
  **1 ステップにつき 1 つの定理・操作しか適用しない。**
- ただし**同一の定理を複数箇所に同時適用する場合**は 1 ステップにまとめてよい。

良い例:

```latex
\begin{aligned}
(a+b)(a-b)
&= a^2 - b^2 \quad(\because \text{分配律}) \\
&= a^2 - (\sqrt{b})^4 \quad(\because \text{平方根の性質}) \\
\end{aligned}
```

悪い例（2 操作を 1 ステップに畳んでいる）:

```latex
(a+b)(a-b) = a^2 - (\sqrt{b})^4
```

### 根拠の明示（各行に何を適用したかを必ず書く）

- **すべての行に、適用した定理・操作を添える。**
- **高校の教科書レベルで自明なもの**（実数の四則演算・分配法則・移項）は省略してよい。
- **本文中で証明済みの Definition / Claim / Theorem の適用は、同じ証明中に何度現れても
  決して省略しない。必ずラベルで参照する。**

構造化テキスト（正本形式）での書き分け:

| 根拠の種類 | 書き方 |
|---|---|
| 式で書ける理由（$\varepsilon^2\le\varepsilon$、$B^{-1}B=I$ 等） | `displayMath` の行末に `\quad(\because \dots)` |
| 短い日本語で足りる理由（分配律・結合律） | `\quad(\because \text{分配律})` |
| **本文の Definition / Claim / Theorem** | **その行で式変形を切り、直前（または直後）の `paragraph` に `ref("<label>")` を置く**。`ref` は数式文字列の中には書けない |

例（実際の書式）:

```ts
paragraph([ref("trace_basic_properties"), " (4) より"]),
displayMath(String.raw`\mathrm{tr}(Q) = \mathrm{tr}(P^{-1}QP) = \mathrm{tr}(D) = r`),
```

**「暗黙に使われている未定義の概念」を残さない。** 使うものは本文に定義がある。

### 階層構造をインデントで可視化する

`\sqrt{\cdot}`、分数、`\begin{pmatrix}`、`\begin{cases}` などのネストは**必ずインデントで表現する**。
各階層 2 スペース、閉じ括弧は対応する開き括弧と同じインデントに置く。
フラットな 1 行に潰さない（読めなくなるため）。

### Step 分割と接続

- 長い証明は Step で区切り、**各 Step は 1 つの中間目標**（中間等式の導出など）に対応させる。
- Step 間は「より、」「特に、」「したがって、」で接続する。

### 記号の帰属を書く（[基本方針_可算コアとℝ脱出](基本方針_可算コアとℝ脱出.md) との接続）

- 登場するすべての記号について**どの集合に属するか**を書く。
- $\mathbb{R}/\mathbb{C}$ が現れる行には、脱出の**脱出の型と理由**を添える
  （書式は [ℝ脱出の台帳と判定手順](ℝ脱出の台帳と判定手順.md) 「書式（本文への記録の仕方）」節）。**これも「各行に根拠を添える」の一部である。**

### 本文とノートの使い分け

- **正しさに必要ならそれは注記ではない。** 定義が意味をもつ条件・適用範囲・well-defined 性・
  主張から従う数学的帰結は `statement`（証明中なら `proof`）に書く。
- 補足計算・具体例・物理的解釈・先行研究との比較・**採用しなかった経路とその理由**は
  `notes/` に置く（最終成果物には載らない）。

## 「SageMath 検証」層 — 式変形を 1 行ずつ確かめる

**「記述」層で書いた式変形を、1 行ずつ機械に確かめさせる。**

### 規約

- `sagemath/check/<対象名>/` に置き、`overview.md` に**対象ラベル**
  （構造化テキスト側の安定識別子）を宣言する。**ファイルパスではなくラベルで紐づける。**
- 式変形 1 行につき 1 ファイル（`check_<内容>.sage`）を原則とする。
  共通定義は `_prelude.sage` に置き `load()` する。
- `overview.md` にはチェック一覧の表（#／ファイル／検証内容／ステータス／結果）を書く。
- 対応が切れていないかは `node sagemath/tools/verify-check-linkage.ts` が機械検証する。

### 厳密計算を優先する

[対数順序群Λ_定義と最小限の道具](対数順序群Λ_定義と最小限の道具.md) の梯子に従い、**可能な限り厳密計算で行う**:

- $\mathbb{Z}/\mathbb{Q}$ → `ZZ`/`QQ`、代数的数 → `QQbar`、$\Lambda$ → 素因数分解（`factor`）。
- $\Lambda$ の等号判定は素因数分解の一致、順序は整数比較。**丸めが原理的に入らない。**
- 浮動小数点（`RR`/`CC`）を使うのは、**$\mathbb{R}$ 脱出を含む量**（実対数・Mahler 測度・
  連続極限）を確認するときだけ。その場合は `overview.md` に**脱出の型を明記する**。
- 許容誤差 `tol` を緩めたときは、**なぜ緩める必要があったかを `overview.md` に書く**
  （例: 成分の絶対値が $10^9$ に達し倍精度の桁が足りない）。

### 検証が失敗したときの扱い

**人手証明の側を直す。** 検証コードを主張に合わせて緩めない。
失敗の記録は消さず、`overview.md` に残す（同じ間違いを繰り返さないため）。

## 「Lean 具体版」層 — 人手証明と 1 対 1 に対応させる

**人手証明と 1 対 1 に対応する厳密証明を書く。人手証明そのものの正当性を保証するのが目的。**

- 抽象度は**人手証明と同じ**に固定する（Ising なら複素行列のまま）。
- **人手証明のどのステップが Lean のどの補題に当たるかを、コメントに人手証明のラベルで書く。**
- **人手証明の計算を mathlib の一般論（群作用・表現論など）へ委ねてはならない。**
  委ねた時点で「1 対 1 対応」の要件違反であり、人手証明どおりの計算に直す。
- `sorry` を残さない（`bash lean/scripts/check-no-sorry.sh` が検査する）。

## 「Lean 必要十分版」層 — 必要十分な抽象度へ再記述する

**具体版と同じ証明手順のまま、登場する対象の抽象度だけを「必要十分なところまで」上げる。**

目的は 2 つ:

1. **何が本質的かを明らかにする。** 例: 交換子と反交換子の恒等式が任意の環で証明できるなら、
   その主張には「行列であること」も「複素数であること」も本質的でない（分配律と結合律で足りる）。
2. **具体版の検査。** 必要十分版を書こうとして必要以上の構造を仮定しないと通らないなら、
   具体版の証明が余計な性質に依存している疑いがある。

### 要件（**満たさないものは必要十分版と認めない**）

1. **証明手順が具体版と同じ**であること。具体版の Step N が必要十分版のどの補題に当たるかを
   両版のコメントに書く。**別の論法へ差し替えたものは、主張が同じでも必要十分版ではない。**
2. **仮定が「具体版の証明が実際に使っている性質」だけ**であること（＝必要十分）。
   使っていない構造（体であること・有限次元性・可換性・行列であること）を仮定に残さない。
   削ったせいで通らなくなる仮定は残し、**なぜ必要かをコメントに書く。**
3. **mathlib の高抽象度の既製定理へ丸投げして主張を出し直すことを禁止する。**
   `:= Mathlib の定理` の一行で終わる宣言や単なる別名定義は必要十分版ではない
   （何が効いているかを一切示さないため）。既製定理との一致を確認したいなら、
   **自前の証明を書いたうえで**一致を述べる補題を 1 本だけ添える。
4. **具体版が必要十分版の特殊化として得られること**を導出ファイルに明示する
   （人手証明と 1 対 1 対応する形の主張は、それとは別に必ず立てる）。
5. **必要十分版は Lean の中だけに置く。** 人手証明の本文にも参照用ノートにも持ち込まない。
6. 要件 1〜3 は**具体版にも対称に適用する**。
7. ファイル冒頭に「**何が効いているか / 効いていないか**」を、
   その証明が実際に使った仮定を根拠として書く。

### 名称についての注意（過去の事故）

以前は「抽象版」と呼んでいたが、その名前が「抽象的な概念を持ち込んで同じ主張を証明し直すこと」と
誤解され、**mathlib の既製の一般論へ丸投げしただけのファイルが書かれる事故が起きた。**
意図は抽象化そのものではなく**必要十分性の見極め**なので「**必要十分版**」と呼ぶ。
Ising プロジェクトでは名前空間 `Ising2D.NecSuf`、ディレクトリ `lean/Ising2D/NecSuf/`、
具体版を導出するファイルは `*FromNecSuf.lean`、記録は `lean/docs/necsuf-*.md`。

## 層をまたぐ規約

- **層をまたぐ紐づけはすべて `labels`（安定識別子）で行う。** ファイルパスに依存させない。
  - 「記述」層のブロックが `labels: ["xxx"]` を持つ
  - 「SageMath 検証」層の `overview.md` が「対象ラベル: `xxx`」を宣言する
  - Lean の両版のファイルがコメントに `xxx` を書く
- **移行・書き換えのときは、ブロック数や参照解決だけを見て「完了」と判断しない。**
  証明の中身が原本から確実に運ばれたかを突き合わせる
  （過去に主要定理の証明が移行漏れで失われた事故がある）。
- **採用しなかった経路は捨てず、ノートへ移し、採用しなかった理由を明記する。**

### 検証コマンド（変更したら全部通す。詳細は [CLAUDE.md](../../CLAUDE.md)）

```sh
(cd structured-latex && npm run check)                    # 生成物の鮮度→型検査→実行時検証→移行漏れ→負テスト
node structured-latex/tools/validate-content.ts           # スキーマ・重複・未解決参照・ノートの targets
node structured-latex/tools/verify-no-lost-proofs.ts      # 移行漏れ検出
node sagemath/tools/verify-check-linkage.ts               # 層1 ↔ 層2 の対応
(cd structured-latex && npm run build:pdf)                # 最終成果物。未解決参照ゼロ・ノート非混入
lake build && bash lean/scripts/check-no-sorry.sh         # 層3・層4
```

## 適用範囲

- **命題・定理として主張するものには、四層すべてを適用する**（「Lean 具体版」「Lean 必要十分版」層は `lean/` を持つプロジェクトのみ）。
- **探索フェーズ**（調査ノート・アイディアの種・gap map）は対象外。Markdown で速く回してよい。
  ただし**種を命題へ昇格させる時点で**、「記述」層の記述ルールと帰属の明示（「記号の帰属を書く（[基本方針_可算コアとℝ脱出](基本方針_可算コアとℝ脱出.md) との接続）」節）を適用する。
- 四層を全部満たせない段階では、**どの層まで済んでいるかを明示する**
  （「「記述」「SageMath 検証」まで。Lean 未着手」）。黙って未検証のまま「証明した」と書かない。
