# 証明の書き方（数学レイヤー）

**証明をどう書き、どう検証するか**についての規律。全プロジェクトに適用する。

## 先に一点（最も誤読されやすい）

> **人手証明は具体に固定する。抽象化は Lean の中だけで行う。**

「抽象度を上げない」（人手証明）と「必要十分な抽象度まで上げる」（Lean）は逆向きに見えるが、
**適用先が違う**。この一点を取り違えると、人手証明が読めなくなるか、
Lean が既製の一般論への丸投げになる。実際に一度事故が起きている。

## ゴール

**丁寧に一つずつ積み重ねて読めば、高校生でも理解できる形で書く。**

これは「厳密であること」と同格の要求であり、**厳密だが読めない証明は失敗**とみなす。

避けたいのは、高い抽象度の道具を持ち込んだせいでその一般論を先に理解する必要が生じ、
**本筋と関係ないところで読者のリソースが尽きること**である。

## 記述の規律

| 規律 | 内容 |
|---|---|
| **一ステップ一定理** | 式変形を絶対に省略しない。移項も四則演算も含め、1 ステップに 1 つの定理・操作しか適用しない。**同じ定理を複数箇所へ同時適用する場合だけ** 1 ステップにまとめてよい |
| **根拠の明示** | すべての行に、適用した定理・操作を書く。高校教科書レベルで自明なもの（四則・分配則・移項）は省略してよい。**本文で証明済みの Definition / Claim / Theorem の適用は、同じ証明中に何度現れても必ずラベル参照で引く** |
| **階層の可視化** | 根号・分数・行列・場合分けのネストは必ずインデントで表す。フラットな一行に潰さない |
| **Step 分割** | 長い証明は Step で切り、各 Step は一つの中間目標に対応させる |
| **記号の帰属** | 登場するすべての記号について所属集合を書く（$\mathbb{N}/\mathbb{Z}/\mathbb{Q}/\Lambda/\overline{\mathbb{Q}}/\mathbb{R}/\mathbb{C}$）。$\mathbb{R}$ が現れる行には**その理由**を添える（指数評価か、極限か、実対数か、完備性か） |

### 新しい道具を入れるときの判断

1. これを理解しないと先へ進めないか。そうでないなら入れない。
2. 本筋か脇道か。脇道の一般論なら具体的な形に落として本文に書く。
3. より初等的に書けるか。書けるならそちらを採る（記述が長くなっても構わない）。
4. 入れるなら、その定義は本文にあるか。**暗黙に使われる未定義の概念を残さない。**

### 抽象度を上げない（人手証明）

主張は具体的な対象について述べる。一般の環・体へ持ち上げない。
理由は、証明が分配則と結合則しか使っていなくても、**述べ方が抽象的なら読者の負担は発生する**から。
「任意の環で成り立つ」と書けば、読者は環の定義と「この対象が環をなすこと」を先に要求される。

## 四層の検証（上の層が下の層を検査する）

| 層 | 何をするか | 何を保証するか |
|---|---|---|
| **記述** | 上の規律で人手証明を書く | 人が一行ずつ追える。省略に嘘が隠れない |
| **SageMath 検証** | 式変形を**一行ずつ**機械に確かめさせる | 書き間違い・符号ミスが残らない |
| **Lean 具体版** | 人手証明と **1 対 1 に対応する**証明 | **人手証明そのものが正しい** |
| **Lean 必要十分版** | 同じ手順のまま抽象度だけ必要十分まで上げる | **何が本質的か**。具体版が過剰な構造を要求していないかの検査 |

### SageMath 検証

- 対象は**ラベル**で紐づける（ファイルパスに依存させない）。`overview.md` に対象ラベルを宣言する。
- **厳密計算を優先する。** `ZZ`/`QQ`/`QQbar`・素因数分解で行い、浮動小数点は
  $\mathbb{R}$ 脱出を含む量を確認するときだけ使う。使ったら理由を記録する。
- 検証が失敗したら**人手証明を直す。** 検証を主張に合わせて緩めない。失敗の記録は消さない。

### Lean 具体版

- 抽象度は人手証明と同じに固定する。
- 人手証明のどのステップが Lean のどの補題かをコメントで対応づける。
- **人手証明の計算を mathlib の一般論へ委ねない。** 委ねた時点で 1 対 1 対応の要件違反。
- `sorry` を残さない。

### Lean 必要十分版

目的は二つ。**何が本質的かを示すこと**（「任意の環で通るなら、行列であることも複素数であることも
本質的でない」）と、**具体版の検査**（必要以上の構造を仮定しないと通らないなら、具体版が
余計な性質に依存している疑いがある）。

満たさないものは必要十分版と認めない:

1. **証明手順が具体版と同じ**であること。別の論法に差し替えたものは、主張が同じでも認めない。
2. **仮定が「具体版の証明が実際に使っている性質」だけ**であること。
   削ったせいで通らなくなった仮定は残し、**なぜ必要かをコメントに書く**（これが検査の本体）。
3. **mathlib の高抽象度の既製定理へ丸投げしない。** 一行で終わる宣言や単なる別名定義は認めない。
   既製定理との一致を見たいなら、自前の証明を書いたうえで一致を述べる補題を一本だけ添える。
4. **具体版が必要十分版の特殊化として得られること**を導出側に明示する。
5. **必要十分版は Lean の中だけに置く。** 人手証明にも参照用ノートにも持ち込まない。
6. 上の 1–3 は**具体版にも対称に適用する**。

> **名称の注意**: かつて「抽象版」と呼んでいたが、その名が「抽象的な概念を持ち込んで
> 証明し直すこと」と誤解され、mathlib へ丸投げしただけのファイルが書かれる事故が起きた。
> 意図は抽象化そのものではなく**必要十分性の見極め**なので「必要十分版」と呼ぶ。
> 実装上の名前空間・ディレクトリの規約は
> [`exact-solution-of-2d-ising-model/README.md`](../../exact-solution-of-2d-ising-model/README.md) を正本とする。

## 補助規律

- **正しさに必要ならそれは注記ではない。** 定義が意味をもつ条件・適用範囲・well-defined 性・
  主張から従う帰結は本文に書く。補足計算・具体例・物理的解釈・先行研究との比較はノートへ。
- **採用しなかった経路は捨てない。** 参照用ノートへ移し、**採用しなかった理由を明記する**。
  後から「なぜこの道を選ばなかったか」を再検討できるようにするため。
- **移行・書き換えのとき、ブロック数や参照解決だけを見て完了と判断しない。**
  証明の中身が原本から確実に運ばれたかを突き合わせる（過去に主要定理の証明を失った事故がある）。

## 適用範囲

- 命題・定理として主張するものには四層すべてを適用する（Lean は `lean/` を持つプロジェクトのみ）。
- 探索フェーズ（調査ノート・アイディアの種）は対象外。Markdown で速く回してよい。
  ただし**命題へ昇格させる時点で**記述の規律と記号の帰属を適用する。
- 四層を全部満たせない段階では、**どこまで済んでいるかを明示する**（「記述と SageMath まで。Lean 未着手」）。
  黙って未検証のまま「証明した」と書かない。
