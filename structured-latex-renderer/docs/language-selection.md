# 言語選択

## 基本原則

**静的解析による型安全が担保されていない言語は使用しない。**

実行前にコンパイラ / 型チェッカが型の整合性を検証できることを、言語選定の絶対条件とする。これは [プログラミング哲学](./programming-philosophy.md) の「エントロピー最小化」、および型システムによるエラーの可視化（[エラーハンドリング戦略](./error-handling-strategy.md)）を成立させる前提である。

2026/06 時点での基本的な選択肢:

| 言語 | 主な用途 |
|---|---|
| TypeScript | FE / BE API / フルスタック |
| Go | BE / CLI / インフラ系ツール |
| Rust | パフォーマンス・安全性が要求される領域 |

> ゲーム等、上記の判断基準が当てはまらない領域は本ドキュメントのカバー範囲外とする。

## フロントエンド

### Web

**TypeScript + React 一択。**

- デザインフレームワークはその時々の要件に応じて選定する。
- 2026/06 時点では **Tailwind CSS + shadcn/ui** を選んでおけばよい。

### Mobile

**React Native を Expo を使用せずに（bare で）導入する。**

- Expo / EAS には依存しない。
- 署名済み native build は React Native CLI / Xcode / Gradle ベースで構成する。

## バックエンド (API)

**特に理由がなければ TypeScript + Node でよい。**

- どの言語を選ぶ場合でも、**大きな web フレームワークを導入しない**。
- Fastify など軽量なルーティング / HTTP レイヤのみを導入し、ビジネスロジックはフレームワークから独立させる（[バックエンドアーキテクチャ](./architecture-backend.md) 参照）。

> インフラ / クラウドの選定は軸が異なるため、[インフラ](./infrastructure.md) で別途定める。
